# Case 001 — Idea-only non-technical project

## Input

```text
I want to organize a yearly community conference that brings local volunteers and nonprofit groups together. Help me define the project properly.
```

## Observed response

```text
From what you have shared, the confirmed context is small but clear:

- This is a yearly community conference.
- It is intended to bring local volunteers and nonprofit groups together.
- The detailed purpose, scope, operating model, and success criteria are not defined yet.

Before drafting documents, the highest-impact questions are:

1. What is the main outcome you want the conference to create — networking, volunteer recruitment, collaboration between organizations, education, fundraising, or something else?
2. Who are the main participant groups, and who is responsible for organizing and making final decisions?
3. What is in scope for the first conference: talks, workshops, booths, volunteer matching, networking sessions, or other activities?
4. What constraints are already known, such as approximate timing, location expectations, budget limits, capacity, accessibility, or safety requirements?
5. How will you know the event was successful — attendance, volunteer sign-ups, partnerships created, participant feedback, or another outcome?

You can answer only what you know. Anything undecided can remain an explicit open question rather than being invented.
```

# Case 002 — Idea-only technical project

## Input

```text
I want to build an online booking platform for independent fitness coaches. Clients should be able to find a coach and book sessions. Help me define the product.
```

## Observed response

```text
The confirmed product context is:

- It is an online booking platform.
- The service is for independent fitness coaches and their clients.
- Clients need to discover a coach and book sessions.

The biggest gaps are still product decisions rather than technical architecture. I would clarify these first:

1. What can each user type do? For example, can coaches manage profiles, availability, pricing, and bookings themselves, and is any administrator role needed?
2. How should coach discovery work in the first version — search/filter by location, specialty, availability, price, online/in-person sessions, or only a simpler directory?
3. What is the booking lifecycle: selecting availability, confirming a booking, rescheduling, cancellation, no-shows, and coach-initiated changes?
4. Are payments part of the initial scope? If yes, what business behavior matters (pay at booking, deposits, refunds, coach payouts) without choosing a payment provider yet?
5. Which notifications or confirmations are essential around bookings, and what outcomes will define a successful first release?

After those are clearer, we can decide whether questions about identity, privacy, integrations, scale, or an architecture overview are necessary. I would not choose frameworks, databases, hosting, or architecture until the product requirements justify those decisions.
```

# Case 003 — Existing requirements review

## Input

```text
I already have a requirements document. Review it for gaps and conflicts, then tell me what questions I still need to answer. Do not rewrite it yet.
```

## Fixture

`evals/project-definition/fixtures/003-existing-requirements.md`

## Observed response

```text
I reviewed the existing requirements. I will not rewrite or save changes yet.

The main findings are:

- Duplicate meaning: FR-003 and FR-004 both describe sending a booking confirmation after a successful booking. They should eventually be consolidated, but I am not changing them now.
- Direct conflict: FR-005 allows customer cancellation up to 24 hours before the appointment, while FR-006 allows cancellation until 2 hours before. The source does not establish which rule is authoritative, so this needs a decision rather than an automatic merge.
- Core booking assumption: FR-001/FR-002 and BR-001 depend on a slot being 'available', but the document does not define what happens if two customers try to book the same slot at nearly the same time or whether availability is revalidated before confirmation. That is an unresolved business/behavior rule, not something I should invent.
- Staff ownership/authorization gap: FR-007 says staff manage appointments 'for their provider', but the document does not define how staff are associated with a provider or whether staff can ever act across providers.
- Scope boundary gap: there are no explicit non-goals, so it is difficult to tell which adjacent features are intentionally outside the first scope.

The highest-priority questions are:

1. Which cancellation rule is intended: 24 hours, 2 hours, or another policy?
2. When two customers attempt the same slot, what outcome should the service guarantee, and should availability be revalidated at booking confirmation?
3. What establishes which provider a staff member is allowed to manage?
4. What should be explicitly out of scope for this version?
5. Is the booking-confirmation requirement intentionally channel-neutral, or is a specific confirmation channel required?

No document changes have been written or published.
```

## Baseline conclusion

The three smoke cases show no obvious contradiction between the written skill and its intended first-turn behavior. The strongest signals are:

- project-type neutrality;
- context-first discovery;
- targeted questioning;
- no premature architecture selection;
- explicit conflict/assumption handling;
- respect for read-only/human-approval boundaries.

Because this is a self-smoke run, it does **not** establish independent behavioral reliability. The next meaningful gate is to execute the same cases in fresh sessions on at least one separate compatible agent and record those results independently.
